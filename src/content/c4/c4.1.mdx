## TL;DR

An agent is a while-loop. Your code calls a model, the model returns either a final answer or a request to call a tool, your code executes the tool and appends the result, and you go around again. That is the core control mechanism; perception, memory and coordination determine what information reaches it. Everything people call "agentic" — ReAct, planning, memory, multi-agent — is a variation on where you put state and who decides what happens next.

One idea organizes the rest: **the model chooses the next action, and your orchestrator decides everything else.** Termination, budgets, retries, what goes into context, which side effects are allowed — all of that is deterministic code you write, not behavior you prompt for. That boundary is where systems assembled out of a framework come apart. The other half of the story is arithmetic: token cost grows quadratically in turn count, latency accumulates serially, and end-to-end success decays geometrically. Those three models expose important design pressures; their assumptions must be checked against actual traces.

## Part 1 — The loop, stripped

**Goal: get the mechanism down to something you can write on a whiteboard in 30 seconds.**

```python
messages = [system_prompt, user_task]
for step in range(MAX_STEPS):
    response = model(messages, tools=TOOL_SCHEMAS)
    messages.append(response)
    if not response.tool_calls:
        return response.text              # termination signal from the model
    for call in response.tool_calls:
        result = execute(call.name, call.args)   # your code, not the model's
        messages.append(tool_result(call.id, result))
raise BudgetExceeded                       # termination guarantee from you
```

Four moving parts. The **model** picks the next action. The **tools** are functions you expose. The **observations** are tool results appended back into the message list. **Termination** happens two ways, and the difference between the two matters more than anything else here.

The model terminates by *choosing not to call a tool*. That is a soft signal — a probabilistic decision that can go wrong in both directions. It can declare success on a half-finished task, or it can keep calling tools forever. The orchestrator terminates by *running out of budget*, which is a hard guarantee because it is a `range()`. Stopping a runaway agent is that distinction plus the caps you enforce around it: max steps, max wall-clock, max cumulative tokens, max spend, and a no-progress detector.

The no-progress detector is the one people forget. Hash `(tool_name, canonical_json(args))` on each call and keep a counter. Three identical calls in a row means the agent is stuck, not working — the tool is returning something the model does not know how to act on, and it is retrying by reflex. Break the loop and surface the state rather than burning the remaining budget.

> **Stop and think.** The loop above appends every tool result to `messages` and never removes anything. What happens to the input token count on turn 12 versus turn 2, and is that growth linear or something worse? Hint: count what gets re-sent, not what gets added.

## Part 2 — Tool calling: how the schema goes in and the call comes back

**Goal: remove the magic from "the model called my function."**

You describe each tool as a JSON Schema. That description is serialized into the prompt — it is text the model reads, on every single turn.

```json
{
  "name": "refund_order",
  "description": "Issue a refund for a delivered order. Use only after confirming the order status is DELIVERED and the refund window is open.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "Order ID, format ORD-XXXXXXXX"},
      "amount_cents": {"type": "integer", "description": "Refund amount in cents, at most the order total"},
      "reason": {"type": "string", "enum": ["damaged", "late", "wrong_item"]}
    },
    "required": ["order_id", "amount_cents", "reason"]
  }
}
```

The model does not execute anything. It emits a structured block naming a tool and an argument object, your runtime parses it, and your code runs the function. Two consequences follow directly.

**First: the description is the prompt.** Tool selection failures are almost never "the model is dumb"; they are two tools whose descriptions overlap, or a description that says what the tool *does* without saying *when to call it*. The fix is to write the trigger condition into the description ("use only after confirming the order status is DELIVERED") and to draw an explicit boundary against the sibling tool. If you have 40 tools and the model keeps picking wrong, the structural fix is fewer, better-bounded tools — or dynamic tool retrieval, where only the relevant handful of schemas is loaded into context per request.

**Second: schema-valid is not semantically valid.** Structured-output enforcement (constrained decoding against the schema) guarantees you get an integer for `amount_cents`. It does not guarantee the integer is the order total rather than the item price, or that the order is refundable at all. Enums and tight types buy you a lot — `reason` can never be a free-text hallucination — but the remaining errors are business-logic errors and belong in the tool, not the prompt. Validate inside `execute()`, and on failure return a `tool_result` marked as an error with a message the model can act on ("amount_cents 4999 exceeds order total 2999"). A failed tool call that returns a useful message is a recoverable turn; one that throws is a dead agent.

### The observation interface is part of the agent

**Goal — treat what the model can see as a design variable.** [SWE-agent](https://arxiv.org/abs/2405.15793) shows the importance of an agent-computer interface: file navigation, bounded search results, editing operations and feedback shape whether a model can complete repository tasks. A shell with enormous raw output and a structured file editor are different experimental systems, even with the same model.

Suppose an edit introduces a syntax error. Returning the affected lines and a parser error gives the next step a repair target; returning a bare nonzero status with 20,000 unrelated log lines may hide it. Compare interfaces with the model, task set and budget held fixed. Track first successful edit, repair attempts and final tests, not just valid tool-call JSON.

## Part 3 — The arithmetic that decides everything

**Goal: put numbers on the three quantities every agent design is priced in — tokens, seconds, and end-to-end success.**

### Tokens grow quadratically in turn count

The API is stateless. Every turn re-sends the entire message list. Let $p_0$ be the fixed prefix (system prompt plus tool schemas) and let each turn append $a$ tokens (the model's tool call plus the tool's result). Turn $k$ sends $p_0 + (k-1)a$ input tokens, so over $n$ turns:

$$
T_{\text{in}} = \sum_{k=1}^{n} \bigl(p_0 + (k-1)a\bigr) = n\,p_0 + a\,\frac{n(n-1)}{2}
$$

The second term is quadratic. Work it with real numbers: $p_0 = 3000$ (a system prompt plus a dozen tool schemas), $a = 700$, $n = 12$.

$$
T_{\text{in}} = 12(3000) + 700\cdot\frac{12 \cdot 11}{2} = 36{,}000 + 46{,}200 = 82{,}200
$$

The 12 generated call/result increments total $12\times700=8400$ tokens, but the repeated inputs total 82,200. At an **illustrative** USD 3 per million input tokens, that is USD 0.2466 before output costs. At 24 turns, $24(3000)+700(24\times23/2)=265{,}200$ input tokens, or USD 0.7956: 3.23× the cost. Doubling approaches 4× only when the quadratic term dominates.

Two levers follow from the formula. **Prefix caching** can reuse both the fixed instructions and a growing unchanged conversation prefix, depending on provider cache rules, minimum lengths and hit rates. It changes billed work and prefill, not the logical input-token count. **Compaction** changes what is resent by dropping or summarizing old observations. Evaluate the information lost during compaction and avoid changing the prefix unnecessarily; caching and compaction interact.

### Latency accumulates serially

Turns are sequential by construction — turn $k+1$ cannot start until turn $k$'s observation exists. With model latency $\ell_m$ and tool latency $\ell_t$, total latency is $n(\ell_m + \ell_t)$. At $\ell_m = 1.8$ s and $\ell_t = 0.4$ s, a 12-turn task takes 26.4 seconds. Caching can reduce model latency, but it does not remove the dependency between turns. A structural lever is fewer serial decisions: batch related work into one tool, run independent tool calls in parallel within a turn, and delete tools that exist to fetch something you could have put in the prompt.

### Reliability decays geometrically

If each step succeeds independently with probability $p$, an $n$-step task succeeds with probability $p^n$:

$$
0.95^{10} = 0.599, \qquad 0.95^{20} = 0.358
$$

A 95% step reliability — which sounds excellent — gives you a 40% failure rate on a 10-step task. Invert it: to hit 90% end-to-end over 10 steps you need $p = 0.9^{1/10} = 0.9895$, so 99% per step. **This is an illustrative independence model, not a forecast of measured completion**, because it reframes every architecture decision as "how do I reduce $n$, or raise $p$." Shortening the trajectory raises end-to-end success more cheaply than any prompt tweak. So does making steps recoverable: a step that fails, returns a legible error, and is retried successfully is not a failed step, which is why error-returning tools change the exponent's base.

## Part 4 — ReAct, and what it actually contributed

**Goal: be able to give the one-paragraph answer without inflating it.**

Reasoning and acting are two different things a model can put in a trace, and the productive move is to alternate them: the model writes a thought, takes an action, observes the result, and repeats, with each observation feeding the next thought. That interleaving is ReAct (Yao et al., 2022). Its contribution was showing that neither half works alone — chain-of-thought reasoning, meaning the model writes out its intermediate steps before answering, hallucinates facts it cannot check when it has no actions available, and action-only prompting has no mechanism for deciding what to do next when the plan needs revising. Interleaving lets the trace be corrected by contact with the environment.

The honest part is that the loop in Part 1 *is* ReAct. Native tool calling absorbed the pattern: the model's internal reasoning plays the role of the "Thought" line, the tool call is "Action", and the appended tool result is "Observation". Native tool APIs can implement this interaction pattern without reproducing the paper’s textual Thought/Action format. Log actions, observations and concise decision records; do not assume that visible reasoning text is a faithful explanation of the model’s internal computation.

## Part 5 — Planning: when it pays and when it is overhead

**Goal: pick between a single loop and a planner-executor with a reason, not a preference.**

A **single loop** decides one step at a time, with full knowledge of every observation so far. A **planner-executor** produces a full plan up front, then executes the steps, then optionally replans.

Planning up front buys you three things. You can *show the plan to a human before anything executes*, and place any required approval before the relevant side effect. You can *parallelize* independent steps because you know in advance that they do not depend on each other. And you can *estimate the budget* before spending it. Those are real, and they are why planner-executor dominates in long-horizon, high-blast-radius workflows.

Planning costs you adaptivity. A plan written at step 0 was written with the least information you will ever have. If step 1's result invalidates steps 2 through 6, you have paid for a plan you must now throw away — and a naive executor will march through the stale steps anyway. So the rule: **plan when steps are independent or the horizon is long enough that drift is the main risk; skip planning when each step's result determines the next.** For a short, predictable task, an additional planning call may buy too little to justify its tokens and latency; test that against the risk of an omitted dependency.

Replanning is the middle ground: keep the plan, but re-derive it whenever an observation contradicts an assumption the plan rested on. Trigger it explicitly (a step failed, a precondition turned out false, the budget forecast blew out), not on every turn, or you have paid for planning and gotten a single loop.

[Agentless](https://arxiv.org/abs/2407.01489) (2024) provides a concrete reason to keep a simple baseline: a structured localization, repair and validation pipeline was competitive on its evaluated software tasks without a fully autonomous loop. That is a historical, benchmark-specific comparison. On your workload, compare a fixed workflow, a single agent and a planner at matched model, tool access, token budget and latency limits.

## Part 6 — Memory: three places state can live

**Goal: stop using "memory" as one word.**

**Context window.** The message list from Part 1. It is working memory: fast, complete, ordered, and quadratically expensive. Everything in it is re-read on every turn, so anything not needed for the *next* decision is pure tax.

**Scratchpad.** A file or key-value store the agent reads and writes through tools. The point is that the content sits *outside* the context window and only the parts it fetches come back in. An agent that writes findings to `notes.md` and greps it later has traded quadratic re-sending for an explicit fetch. It is also the cheapest fix for a chatbot that loses the thread after ten turns: summarize on a threshold, keep the last $k$ turns verbatim — $k$ being a small recency window, six to eight turns — plus a pinned facts block, and push the rest to the scratchpad where it can be retrieved on demand.

**External store.** Persistent memory across sessions, retrieved by relevance. Split it two ways: *episodic* (what happened — "on 2026-03-04 the user asked to cancel order ORD-771") and *semantic* (durable facts — "the user prefers metric units"). Short-term is the first two; long-term is this one.

Long-term memory pollutes in a specific, predictable way: the agent writes a wrong inference once, retrieves it later as established fact, reasons from it, and writes a second wrong fact downstream. The defenses are all about the write path, not the read path. **Gate writes** — only persist facts a user confirmed or a tool verified, never the model's unverified inference. **Store provenance and timestamps** so a later reader can tell a confirmed fact from a guess. **Deduplicate on write** — update the existing note rather than appending a contradicting one. **Decay**, so stale preferences expire instead of accumulating. And keep a read path that lets you show a user what is stored and delete it.

### External context can be a program input

**Goal — explain recursive context access without claiming unlimited memory or reasoning.** [Recursive Language Models](https://arxiv.org/abs/2512.24601), first posted on 31 December 2025 and revised in 2026, places long context in an external environment the model can inspect programmatically and query through recursive model calls. This changes the access strategy rather than enlarging each invocation's context window. Track what spans were inspected, cap recursive depth and total tokens, and preserve evidence pointers: decomposition can miss a cross-part dependency or lose it in a summary. Contrast this editable/external memory with Engram's architectural lookup memory in [c3.2](/c/c3/c3.2).

## Part 7 — Multi-agent: measure what the extra agents buy

**Goal — separate useful parallel work from coordination overhead.** A multi-agent system delegates work to other model-controlled loops. Three plausible benefits are **parallelism**, **context isolation**, and **complementary evidence or skills**. None follows merely from increasing agent count.

For an illustrative four-part research task, four independent 4-second searches take 16 seconds serially, or about 4 seconds plus 2 seconds to combine results when run in parallel. If each search needs the previous result, the dependency chain still takes 16 seconds and coordination adds delay. Repeated prefixes, worker traces and synthesis also consume tokens; isolated contexts help only if summaries preserve the evidence needed by the parent.

<ResearchBars variant="parallel" />

The controlled study [Towards a Science of Scaling Agent Systems](https://arxiv.org/abs/2512.08296) (December 2025) finds task- and topology-dependent gains, including regressions on sequential work. Its empirical thresholds belong to its tested configurations. The February 2026 preprint [Understanding Agent Scaling via Diversity](https://arxiv.org/abs/2602.03794) finds that correlated homogeneous agents saturate sooner than configurations bringing complementary information. Different role names alone do not demonstrate independent evidence.

Keep a single-agent baseline. Hold total compute and tool access fixed, then measure success, critical-path latency, token cost and first handoff failure. A second agent earns its place when those measurements improve the intended tradeoff, rather than when a diagram looks more sophisticated.

## Part 8 — MCP, in one paragraph

Without a shared convention, every agent framework writes its own connector to every system it touches: with $n$ agent frameworks and $m$ systems that is $n \times m$ integrations, so ten of each means a hundred. A shared protocol collapses it — each system ships one server, each agent ships one client, ten plus ten. MCP (Model Context Protocol, introduced by Anthropic in November 2024) is that protocol: an open standard for exposing tools and data sources to models over a uniform interface. That is the whole pitch. Know that it makes integrations portable, know that it does not change anything about the loop in Part 1, and do not memorize the transport layer.

## Part 9 — Users and agents can change the same world

**Goal — distinguish a coordination mistake from a tool or perception failure.** [tau2-bench](https://arxiv.org/abs/2506.07982) (2025) models a user and an agent acting in a shared environment. In a support scenario, the agent changes an account setting while the user resets a device. The next diagnostic step must check both outcomes: “I sent the instruction” is not evidence that the reset happened. Use observable state, acknowledgments and preconditions before continuing.

[OSWorld](https://arxiv.org/abs/2404.07972) (2024) adds another distinction for computer-use agents: a click can be well formed but aimed at the wrong visible control. Label failures separately as **perception/grounding** (wrong control), **action execution** (correct target, operation failed), or **coordination** (user and agent acted on incompatible state). Final-state checks and step traces make those diagnoses possible. See [c4.2](/c/c4/c4.2) for repeated-run evaluation.

## Tradeoff matrix

| Decision | Option A | Option B | Pick A when | Pick B when |
|---|---|---|---|---|
| Control flow | Fixed workflow (code) | Agent loop (model decides) | Steps are known in advance | Path depends on what you find |
| Loop shape | Single loop | Planner-executor | Under ~4 steps, branchy | Long horizon, parallelizable, needs approval |
| Tool granularity | One broad tool | Several narrow tools | Args are simple, calls are frequent | You need per-action gating and clear selection |
| History | Keep full context | Compact / scratchpad | Under ~10 turns | Long runs, or $a\,n^2/2$ dominates cost |
| Memory | Context only | External store | Single session | Facts must survive sessions |
| Agents | Single agent | Multi-agent | Almost always | Separable, read-heavy, parallel sub-tasks |
| Stop condition | Model says done | Orchestrator caps | Never rely on this alone | Always, in addition |

## Production failure modes

1. **Non-termination from an ambiguous tool result.** A tool returns `{"status": "pending"}`; the model reads it as "not done yet" and re-calls the same tool forever. Cost: the full step budget, every time. Fix: make tool results state the next action explicitly, and add the identical-call-hash detector.
2. **Duplicated side effects on retry.** A payment tool times out after the charge succeeded. The model retries, and the customer is charged twice. Fix: idempotency keys — a deterministic key derived from the task and arguments, sent with the call so a repeat returns the first result instead of acting twice — enforced in the tool, not in the prompt.
3. **Context blowout past the window.** A loop that greps a large repo appends 30k-token tool results until the request exceeds the context limit and errors mid-task. Fix: truncate tool results at the boundary with a pointer to the full content, and compact on a token threshold.
4. **Tool selection collapse as the catalog grows.** Accuracy is fine at 8 tools and falls apart at 40, because three of them plausibly match the request. Fix: merge overlapping tools, write trigger conditions into descriptions, or load schemas dynamically.
5. **Silent staging-to-prod drift.** A downstream API adds a field and changes an enum value. The schema still validates, the model still calls the tool, and the results are quietly wrong. Fix: version tool contracts, and assert on response shape inside the tool.
6. **Long-term memory poisoning.** An unverified inference gets written to the store, retrieved three sessions later as fact, and reasoned from. Fix: gate writes, store provenance, decay entries.
7. **Cost blowup with no ceiling.** A single hard task loops 60 times; the quadratic term dominates and one request costs more than a thousand normal ones. Fix: a cumulative-token cap enforced in the orchestrator, checked before every model call.

## Interview gotchas

- **"What's the difference between an agent and an LLM chain?"** A chain has a control flow you wrote; an agent's control flow is chosen by the model at run time. That difference is the whole thing: the agent can adapt, and it can also loop forever, so it needs caps a chain never needed.
- **"How do you stop an agent from running forever?"** Two termination paths. The model's is soft and can fail. Yours is hard: max steps, max tokens, max wall clock, max spend, plus a repeated-call-hash detector for the stuck case. Say the numbers you would set.
- **"What logic belongs in the orchestrator versus the LLM?"** Anything deterministic, anything with a correctness guarantee, and anything with a blast radius. Retries, idempotency, budget caps, permission checks, routing on a known enum — all orchestrator. The model decides only what genuinely requires judgment over unstructured input.
- **"Your agent picks the wrong tool among many."** Diagnose before fixing: log the chosen tool and args on every call, and look at whether the *right* tool is even plausible from its description. Usually it is a description overlap. Then narrow descriptions with trigger conditions, merge near-duplicates, and if the catalog is large, retrieve schemas per request instead of loading all of them.
- **"Right tool, wrong arguments."** Tighten the schema first (enums, required fields, formats in descriptions) and turn on structured-output enforcement. Then validate semantics inside the tool and return an actionable error so the model can correct on the next turn. Add a couple of example calls to the description if the argument shape is unusual.
- **"When is an agent the wrong solution?"** When the steps are known in advance. If you can draw the flowchart, write the flowchart — you get determinism, lower cost, lower latency, and a debuggable stack trace. The refusal is the answer, not a caveat.
- **"When do you go multi-agent?"** Compare a single-agent baseline with separable parallel work, context isolation or complementary evidence. Measure success and latency at matched total budgets; extra coordination and correlated errors can negate the gain.
